# `/gh-fix-review`

GitHub の PR に付いた **Review comment（差分の行に付くコメント）** を取得し、対応・push まで
通したうえで、**各スレッドに必ずインライン返信する**。

```
/gh-fix-review 3479 --loop 3
```

「必ず返信する」をエージェントの善意ではなく**終了コードによる検証**で担保する。
返信済みかどうかの判定・投稿は、すべて `pr-reply.sh` の終了コードで行う。文言では判定しない。

## スコープ

含む: 未返信スレッドの取得 / 各指摘の妥当性検証 / 分類とユーザーへの提示 / 修正の実装 /
セルフレビュー / PUSH 前ゲート / commit と push / 各スレッドへのインライン返信 /
未返信ゼロの検証 / 再レビュー起動（トリガー文字列は「リポジトリ固有の設定」参照）と結果待ちのループ。

含まない: Issue comment（会話タブの通常コメント）への返信、Review summary
（"Changes requested" の本文）への返信 — どちらもスレッドが存在せずインライン返信できない。
ローカル Codex の指摘（`findings-<N>.json`、これは `/gh-fix-issue` の担当）。
レビュースレッドの resolve（閉じる判断はレビュアーのもの）。PR のマージ。
人間のレビューを待つポーリング（待ち時間が無限になりうるため行わない）。

## 前提ツール

- `gh`（GitHub CLI。認証済みであること）
- `jq` **1.6 以上**。`--list` / `--verify` の判定ロジックは `threads.jq` に閉じており、
  そこで `INDEX` 組み込み関数を使っている。jq 1.6 未満では動かない。
  `jq --version` で確認できないバージョンの環境では先に導入すること。

## スクリプト

フローが呼び出すコマンドは4つ。

- `${CLAUDE_PLUGIN_ROOT}/skills/gh-fix-review/pr-reply.sh` — スレッドの状態取得と返信投稿。判断はしない、
  入出力と終了コードだけを担う素の GitHub API ラッパー
- `gh` — PR 未追跡箇所の確認・再レビューのトリガー投稿（`gh pr comment`）・再レビュー待ちの
  ポーリング（`gh api`）
- `git` — カレントブランチと push 状態の確認
- `${CLAUDE_PLUGIN_ROOT}/skills/gh-fix-review/gates.sh` — PUSH 前ゲート。プラグイン同梱

```
pr-reply.sh --check   [--pr N]                    前提確認
pr-reply.sh --list    [--pr N]                    未返信スレッドを JSON で出力
pr-reply.sh --verify  [--pr N]                    未返信が残っていないか
pr-reply.sh --reply <comment_id> --body-file <path>
```

終了コード:

| code | 意味 |
|---|---|
| 0 | 未返信なし / 投稿成功 / 前提確認 OK |
| 10 | 未返信あり（一覧を stderr に出す） |
| 30 | `gh` が使えない / `jq` が使えないか古すぎる / PR が見つからない / カレントブランチが PR の head でない / 未コミットの変更がある |
| 1 | 実行失敗 |

**10 を返すのは `--verify` のみ。`--list` は未返信があっても 0 を返す**ので、件数や中身は
`--list` の出力 JSON（配列の長さや要素）で判断すること。終了コードで分岐しない。

exit 30 の「未コミットの変更がある」判定は `git status --porcelain --untracked-files=no` を使う。
**未追跡の新規ファイルはこの判定に含まれない**（追跡済みファイルの変更・ステージ済みの変更のみを見る）。

契約は 0 / 10 / 30 / 1 のみ。表に無い終了コード（`jq` の失敗による 2 や 3 など）が返ったら
**1 と同様に「実行失敗」として扱い、停止する**。

### テスト専用の環境変数

`PR_REPLY_FIXTURE`（`gh` を呼ばずコメント一覧をこの JSON ファイルに差し替える）と
`PR_REPLY_SELF`（`gh api user` の代わりに使うログイン名）はテスト専用。設定されていると
スクリプトは警告を stderr に出す。**これらが設定されているとき、その判定は実際の GitHub
では検証されていない。通常の運用では絶対に設定しないこと**
（CLAUDE.md の `PREFLIGHT_SKIP_KTLINT` と同じ扱い）。

`--list` が返す各スレッドの形: `thread_root_id` / `path` / `line` / `outdated` /
`url` / `root_author` / `last_author` / `body` / `comments`。
**返信先には `thread_root_id` を渡す**（スレッドの途中の comment_id ではない）。

**返信本文は必ずファイル経由で渡す**（`--body-file`）。改行や引用符を含む日本語の
本文をシェル引数として渡すと壊れるため、一時ファイルに書いてからパスを渡す。
本文の生成は呼び出し側（Claude）の仕事で、スクリプトは投稿するだけ。

## 全体フロー

| # | ステップ | 担当 |
|---|---|---|
| 0 | `gh` 認証・PR 解決・作業ツリーの確認（`pr-reply.sh --check`） | script |
| 1 | 未返信スレッドの取得（`pr-reply.sh --list`） | script |
| 2 | **各指摘が妥当かを検証する**（下記「指摘の妥当性判断」） | Claude |
| 3 | 「対応する / 見送る」に分類し、ユーザーに提示して**承認を得る** | Claude |
| 4 | 修正の実装 | Claude |
| 5 | セルフレビュー → 自己指摘を対応 | Claude |
| 6 | PUSH 前ゲート（build / test / ktlint） | script |
| 7 | commit → push → push 成功の確認（`git rev-parse HEAD` と `git rev-parse @{u}` の一致） | Claude |
| 8 | 各スレッドへインライン返信（`pr-reply.sh --reply`） | script |
| 9 | 未返信ゼロの検証（`pr-reply.sh --verify`） | script |
| 10 | **LOOP** 残り周回があれば再レビューのトリガー文字列（「リポジトリ固有の設定」参照）を投稿し、新しい指摘を待って1へ | Claude + script |

ステップ 3 で一度止まる。push と返信はどちらも取り消しにくい外向きの操作であり、
何を直し何を見送るかはユーザーの判断を要するため。ステップ 4 以降は通しで走る。

**ステップ0で解決した PR 番号は、以降のすべての `pr-reply.sh` 呼び出しに `--pr N` で
明示的に渡す。** 各呼び出しが独立に PR を再解決すると、実行タイミング次第で意図しない
PR に紐づく可能性があるため。

ステップ 5 のセルフレビューは `REVIEW.md` とプロジェクト CLAUDE.md の
「コミット前に確認すること」を基準とする。`/gh-fix-issue` のセルフレビューと同じ基準。

コミット粒度は1周につき1コミット。squash はしない。どの指摘にどう対応したかを
履歴に残すため。

ステップ 7 の push 成功確認は、push 失敗やリモート未反映のまま次に進まないための
ガード。`git rev-parse HEAD` と `git rev-parse @{u}` が一致しなければ返信に進まない。
一致しないまま返信に進むと、リモートに存在しない SHA を「反映: <SHA>」として公開 PR に
投稿することになり、返信は取り消しにくい操作であるため。

以下、各ステップのうち手順が複雑なもの（妥当性判断・返信本文・ループ制御・ゲート・
中断条件）を詳述する。

## 指摘の妥当性判断

**修正に着手する前に、各指摘が妥当かどうかを必ず判断する。** レビューコメントは
自動レビューの誤検知や、レビュアーの読み違いを含みうる。指摘されたから直す、という
進め方をしない。

### 判定は3値

| 判定 | 意味 | その後 |
|---|---|---|
| 妥当 | 指摘のとおり問題がある | 修正する |
| 妥当でない | 指摘の前提がコードと合っていない | 修正せず、**根拠を添えて返信する** |
| 判断保留 | コードを読んでも確証が得られない | ユーザーに提示して判断を仰ぐ |

「妥当でない」と「判断保留」を混同しない。両者は返信の要否ではなく扱いが異なる
（前者は根拠を添えて返信して次に進む、後者はユーザーに判断を仰ぐまで先に進めない
= 中断条件に該当する）。

### 確認する項目

各指摘について、次の4つを確認する。

- 指摘が参照している行・シンボルが**実際に存在するか**（outdated な指摘では特に）
- 指摘の前提（「この値は null になりうる」など）がコードと合っているか
- リポジトリの規約（`CLAUDE.md` / `REVIEW.md`）と矛盾しないか
- 指摘のとおり直すと、別の既存挙動を壊さないか

### 規則

**憶測で「妥当」と判定しない。** 必ず該当コードを読んで裏を取る。裏が取れなければ
「妥当でない」ではなく「判断保留」にする。誤った指摘を握りつぶすリスクと、
正しい指摘を見落とすリスクの両方を避けるため。

**「妥当でない」と判断しても、黙って無視しない。** 根拠を添えて必ずインライン返信する。
これは「必ず返信する」という要件の一部であり、レビュアーが反論できる状態にしておくため。

この考え方は `codex-review.sh --discuss`（指摘が誤っていると考えたときに反論して
見解を求める口）と同じ。違いは、あちらがローカル Codex への反論であるのに対し、
こちらは GitHub 上のスレッドへの返信になる点。

## 返信本文

見送る指摘にも**必ず返信する**。「必ずインライン返信」を、対応したものだけの話に
しないため。返信本文の型は3種類ある。

**対応した場合:**

```
<何をどう直したか>

反映: <commit SHA>
```

**見送る場合:**

```
<なぜ見送るか>
```

**指摘が妥当でないと判断した場合:**

```
<指摘の前提がコードとどう食い違っているか>

該当箇所: <ファイル:行> の <実際のコード>
```

根拠を示す。「対応不要です」だけで済ませない。

言語はリポジトリの規約に合わせる（下記「リポジトリ固有の設定」参照。既定は日本語）。

本文は呼び出し側（Claude）が作る。スクリプトは投稿するだけで、文面の生成には関与しない。
本文はファイルに書いてから `pr-reply.sh --reply <thread_root_id> --body-file <path>` に渡す。

## ループ制御

```
/gh-fix-review [PR番号] [--loop N]        N 省略時は 1
```

1周 = 「取得 → 分類 → 修正 → セルフレビュー → ゲート → push → 返信 → 検証」。

```
for i in 1..N:
    threads = list_unreplied()

    if threads が空:
        i == 1 なら「対応すべき指摘なし」として終了
        i > 1  なら正常終了
        break

    妥当性検証 → 分類 → ユーザー承認 → 修正 → セルフレビュー → ゲート → commit → push → 返信
    verify で未返信ゼロを確認（残っていたら停止）

    if i == N:
        上限到達として終了

    再レビューのトリガー文字列（「リポジトリ固有の設定」参照）を投稿
    新しい review comment の出現を待つ（タイムアウトで停止）
```

### 継続・停止の条件

| 状況 | 挙動 |
|---|---|
| 再取得で未返信ゼロ | 正常終了（残り周回があっても終わる） |
| 未返信あり & 残り回数あり | 次の周へ |
| 未返信あり & 上限到達 | 停止して報告（残った指摘を一覧で出す） |
| 再レビュー後の未返信が前周と同一 & 修正コミットが発生しなかった | 停止（無限ループ防止） |

最後の行は、全ての指摘を「見送り」にした場合に効く。修正が入っていないので
再レビューは同じ指摘を繰り返し、トリガー文字列（「リポジトリ固有の設定」参照）を
投げ続けるだけの周回になる。

### 再レビューの起動

`--loop N`（N ≥ 2）のときのみ、周の最後に PR のトップレベルコメントとして
再レビューのトリガー文字列（下記「リポジトリ固有の設定」参照）を投稿する。
Claude Code Review を Manual 運用しているリポジトリでは、**投稿しない限り再レビューは走らない**。
自動レビューが無いリポジトリでは、この節は使わず既定の `--loop 1` で運用する。

既定1周では投稿しない。マネージドレビューを消費する外向きの操作であり、
明示的に `--loop N` と書いた場合のみのオプトインとする。

### 待ち方

投稿時刻より後に作成された review comment が現れるまでポーリングする。**`pr-reply.sh` に
新しいモードは追加しない**（実 GitHub での検証をまだ一度も行っていない段階で、テストできない
新規経路を足すのは順序が逆のため）。以下の `gh` コマンド列をそのまま使う。

```bash
# 投稿前に基準時刻を記録する
SINCE="$(date -u +%Y-%m-%dT%H:%M:%SZ)"

# 再レビューを起動する（トリガー文字列は「リポジトリ固有の設定」参照。例は @claude review）
gh pr comment <PR番号> --body "@claude review"

# 20秒間隔・600秒上限でポーリングする
ELAPSED=0
COUNT=0
while [ "$ELAPSED" -lt 600 ]; do
  sleep 20
  ELAPSED=$((ELAPSED + 20))
  COUNT="$(gh api "repos/{owner}/{repo}/pulls/<PR番号>/comments" \
    --jq '[.[] | select(.created_at > "'"$SINCE"'")] | length')"
  if [ "$COUNT" -ge 1 ]; then
    break
  fi
done

if [ "$COUNT" -lt 1 ]; then
  echo "600秒待っても新しい review comment が現れませんでした。停止します。" >&2
  # ここで停止してユーザーに提示する（fail closed）。ループを続行しない。
fi
```

- 間隔: 20秒
- タイムアウト: 600秒（10分）
- タイムアウトしたら**停止して報告**する（fail closed）

人間のレビューは待たない。待ち時間が数時間〜数日になりうるため。終了時には
「未返信ゼロ / 再レビューは起動済みか未起動か」を明示し、状態が曖昧に終わらないようにする。

## PUSH 前ゲート

**プラグイン同梱の `gates.sh` を実行する。** リポジトリ側の準備は要らない。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/skills/gh-fix-review/gates.sh" > /tmp/gates.log 2>&1; echo "EXIT=$?"
cat /tmp/gates.log
```

このスクリプトが 3 段階で検証内容を決める。

1. `<repo-root>/.claude/gh-fix-review.gates.sh` があれば委譲する（**任意**。このプラグイン専用の上書きで、他プラグインのファイルには反応しない）
2. 無ければプロジェクト形式を検出する（`gradlew` → `./gradlew test` など）
3. 検出できなければ**警告して続行**する

**出力をパイプ（`| tail` 等）に通さないこと。** 終了コードを取り損ねる。
ファイルへリダイレクトし、直後に `$?` を取ってから内容を読む。

| exit | 扱い |
|---|---|
| 0 | 合格。push へ進む |
| 10 | 不合格。原因を直してコミットし、再実行（修正は最大2回・実行は最大3回） |
| 1 | ゲートの実行基盤自体の問題。直して再実行する対象**ではなく**、**停止してユーザーに提示** |

exit 10 と exit 1 を混同しない。exit 10 は「コードに直すべき原因がある」状態で、
修正してコミットし直せば解消しうる。exit 1 は「ゲートそのものが実行できていない」状態
（設定不備・環境の問題など）で、コードを直しても解消しない。
exit 1 が出たら修正を試みず、そのまま停止してユーザーに提示する。

**段階 3（検出できなかった）で `0` が返ったときは、「ゲート未実行」を返信本文と
ユーザーへの報告に明記する。** 検証していないことを隠さない。黙って「対応しました」と
返信しない。

段階 1 の上書きは速度のために置く。実地検証した大規模 Android リポジトリでは
狙い撃ちが 3 秒に対し汎用の `./gradlew test` が 250 秒だった
（触らないフレーバーの kapt まで回るため）。
遅さが問題になったリポジトリだけが置けばよい。

他のプラグイン（`gh-fix-issue` など）のスクリプトを探して呼ばないこと。
片方のプラグインしか入れていない利用者が壊れる。


## 中断条件

以下に該当したらフローを停止し、ユーザーに提示する。

1. 未コミットの変更がある
2. `gh` が未認証、または PR が見つからない
3. カレントブランチが PR の head ブランチでない
4. 指摘の意味が不明瞭で、対応方針を決められない
5. 指摘の妥当性が「判断保留」になった（コードを読んでも確証が得られない）
6. ゲートが2回直しても通らない
7. ゲートが exit 1 を返した（実行基盤の問題）
8. 再レビュー待ちがタイムアウトした
9. `--verify` が push 後も未返信を検出した
10. 再レビュー後の未返信が前周と同一で、修正コミットも発生しなかった
11. push に失敗した、またはローカル HEAD が upstream に反映されていない

## リポジトリ固有の設定

このスキルは ai-dev-market から複数のリポジトリへ配布される。**リポジトリによって変わる値は
下の3つだけで、他の節はすべてここを参照するだけにしてある。** 新しいリポジトリで使い始める
ときは、まずこの表を確認する。

| 項目 | 既定（実地検証済み） | 別のリポジトリで確認すること |
|---|---|---|
| PUSH 前ゲート | プラグイン同梱の `gates.sh` を実行する（リポジトリ側の準備は不要） | 遅い場合や検証内容を固定したい場合のみ `.claude/gh-fix-review.gates.sh` を置いて上書きできる |
| 再レビューのトリガー文字列 | PR のトップレベルコメント先頭に `@claude review`（Claude Code Review を Manual 運用しているリポジトリ向け） | 起動方法が違う、または自動レビューが無いリポジトリでは既定の `--loop 1` で使い、再レビュー待ちを使わない |
| 返信の言語 | 日本語 | そのリポジトリの規約に合わせる |

これ以外にリポジトリ固有の前提は持たない。`pr-reply.sh` は `gh` がカレントディレクトリの
remote から owner/repo を解決するため、どのリポジトリでもそのまま動く。

## 既存の仕組みとの関係

**このフローは既存のファイルを一切変更しない。**

| 対象 | 扱い |
|---|---|
| `<repo-root>/.claude/gh-fix-review.gates.sh` | **あれば**実行する。無くても動く |
| 他のプラグイン（`gh-fix-issue` など） | **参照しない。** 片方だけ入れた利用者が壊れるため |
| `.claude/settings.json` の hook | 触らない |
| `CLAUDE.md` / `REVIEW.md` | 触らない |
| `AGENTS.md` | **作らない**（Codex の自動レビューが読む文脈を変えてしまうため） |

Codex が自動でインライン返信する配線はこのスキルのスコープに含めない。`pr-reply.sh` は
エージェント非依存の素の CLI であり、Codex からでも人間からでも同じコマンドで叩ける。
